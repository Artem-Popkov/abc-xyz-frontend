# Решения и допущения фронтенда

Что решено и почему. Пункты, которые ещё нужно подтвердить у команды, помечены **«не согласовано»**.

## История

- **Версия 1** (до 25.10.2026): свой формат CSV (`sku, name, period, quantity, price`), своя методика, экран сверки Python и 1С.
- **Версия 2** (25.10.2026): редизайн, формат данных кейса и методика бэкенда, выкладка на GitHub Pages. Экран сверки Python и 1С убран из интерфейса (см. ниже).

## Методика расчёта (как в программе бэкенда)

| Что | Решение |
|-----|---------|
| Выручка | Σ qty × price за период |
| Сортировка | По убыванию выручки, при равенстве — по `item_code` |
| ABC | По накопленной доле **до** товара: `< 80 %` → A, `< 95 %` → B, иначе C. Доля округляется до 6 знаков. Первый товар всегда A |
| Период | От первого до последнего месяца с продажами, либо `from`/`to` из настроек |
| Месяцы без продаж | Считаются нулём |
| CV | σ / μ, σ по N месяцам (не N − 1), округление до 6 знаков |
| XYZ | `CV < 0.10` → X, `< 0.25` → Y, иначе Z. Меньше 3 месяцев с продажами → «–» (не классифицирован) |
| Товары без продаж | Остаются в отчёте: выручка 0, класс `C-` |
| Пороги | Настраиваются на экране «Данные», уходят в запросе (`params`). В программе бэкенда пока зашиты — нужно вынести (см. «Открытые вопросы») |

Расчёт сверен вручную на тестовом наборе бэкенда (6 товаров, 34 строки продаж): классы и CV совпадают с формулами бэкенда (P001 — AY, CV 0,132665; P003 — B, хотя начинается ровно с 80 %; P004 — B-, P006 — C-). Автоматическое сравнение с выводом программы бэкенда (Go) не проводилось.

Раньше фронт относил товар к A, если накопленная доля **с ним** ≤ 80 %. На границе это даёт другой класс, поэтому фронт переведён на правило бэкенда.

## Данные

- Формат кейса: `items.csv` + `sales.csv` (подробно в `docs/data-format.md`).
- Строки с ошибками пропускаются с сообщением, а не отклоняют весь файл, — как у бэкенда.
- Фронт разбирает CSV сам и отправляет на бэкенд JSON (`items[]`, `sales[]`), а не файлы. Так проще показать ошибки сразу, до отправки.
- Пример данных генерируется детерминированно (`src/mocks/sampleData.js`): 150 товаров в 12 категориях, 5855 строк продаж (кейс требует ≥ 1000). Есть сезонные товары с XYZ «–» и товар без продаж.

## Сверка с 1С — убрана из интерфейса

По архитектуре проекта результаты Python и 1С сверяются **на бэкенде**, а на фронт приходит итог. Кейс сверку тоже не требует («без интеграций с учётными системами»). Поэтому экран «Сверка» удалён: фронт показывает один результат. Если бэкенд решит передавать информацию о расхождениях, её можно вывести отдельным блоком — **не согласовано** (см. «Открытые вопросы»).

## Интерфейс

- Стиль Apple TV / tvOS: стеклянные карточки (`backdrop-filter`), фон со свечением, крупная типографика Inter, эффект «фокуса» при наведении.
- Темы: светлая и тёмная, по умолчанию как в системе, выбор хранится в `localStorage`. Если `localStorage` недоступен, тема просто не запоминается.
- `prefers-reduced-motion`: анимации и набегающие числа отключаются.
- Экраны: обложка → «Данные» → «Результаты». Дашборд: KPI, матрица 3×3 (клик по группе фильтрует таблицу), Парето с цветом по ABC, сводка долей A/B/C и X/Y/Z со средним CV, таблица с поиском и фильтрами (категория, ABC, XYZ), экспорт CSV.
- На дашборде показаны параметры, с которыми фактически считали (из ответа бэкенда), и дата расчёта — требование кейса «трассируемость».
- Экспорт: `item_code, name, revenue, abc, cv, xyz, class`, разделитель `,`, UTF-8 с BOM (чтобы Excel открыл кириллицу). У товаров с XYZ «–» поле `cv` пустое.
- Проверено в Chrome: обе темы, ширина 1440 и 390 px, без горизонтальной прокрутки и ошибок в консоли.

## Выкладка

- GitHub Pages через Actions (`.github/workflows/deploy.yml`): сборка на push в `main`.
- `base: './'` в `vite.config.js` — относительные пути, работает при любом имени репозитория.
- На Pages сайт работает на моке (`VITE_USE_MOCKS` не задан → мок).

## Что не сделано

- **Пузырьковая диаграмма для XYZ** (есть в кейсе, не вошла в объём MVP). Можно добавить на Recharts.
- **Фильтр по диапазону выручки** (есть в кейсе). Сделаны фильтры по периоду, категории и классу.
- **Роли** (аналитик меняет пороги, остальные смотрят) — нужна авторизация, а её тимлид запретил до конца MVP.
- **Прогнозы, нейросети, микросервисы** — запрещено тимлидом.
- **Подключение к реальному бэкенду** — бэкенд пока консольная программа, а не HTTP-сервер.
- **Размер бандла** ~930 kB (Vite предупреждает о > 500 kB). Для MVP не критично, можно разбить на части позже.

## Открытые вопросы

- HTTP-сервер бэкенда `POST /api/analysis` по `docs/api-contract.md`: пороги ABC/XYZ в параметрах запроса, CORS для `http://localhost:5173` и GitHub Pages, окончательный набор полей ответа.
- Поведение бэкенда при расхождении расчётов Python и 1С: использовать один из расчётов, возвращать ошибку или передавать расхождения на фронт.
- Совпадение порогов и правила «накопленная доля до товара» в 1С: при различиях классы на границах 80 % и 95 % будут расходиться.
